# Task Tracker

Every work item gets three files. Never fewer. **Two live in the work-item folder. The third does not.**

| File | Where | Holds | Who reads it | Size |
|---|---|---|---|---|
| `tracker-<slug>-<date>.md` | the work-item folder | Tasks. Nothing else. | Agents, every session. | `60 + (30 x phases) + tasks` lines. |
| `implementation-<slug>-<date>.md` | the work-item folder | Every detail. | Agents, before writing code. | No limit. |
| `<slug>.html` | `project-files/human/` | The same plan, readable by a human. | **The owner. Never an agent.** | No limit. |

**The page is deliberately outside the work-item folder.** An agent that lists the folder, or globs `implementation-*`, must never see it - it costs about 8,000 tokens of context and holds nothing the two Markdown files do not. Nothing in either Markdown file points at it. Its path is derived from the `slug`. **ADR 0052.**

The tracker answers: what phase are we in, what task is next, what is done, what is proven by tests, what is stuck.

The implementation document answers: why, what exactly changes, where in the code, how to build it, how to check it.

The HTML page answers the owner's question - *what is going on and what do you need from me* - without making them read Markdown. **It is generated by `scripts/build-page.py` from the two Markdown files.** If they disagree, the Markdown wins. It also carries one runnable prompt per open task, so a model can pick up the work without being re-briefed.

**The tracker never holds prose. The implementation document never holds live task state.** They link both ways.

Copy the shapes from `references/`. Do not invent your own layout.

## What a phase is

**A phase separates work. One phase is one piece of work. Never mix two.**

Finish this sentence in plain words: *"When this phase is done, ______ works."*

If you need the word **and** to finish it, it is two phases.

Name a phase after what works when it is finished. Never after a layer, a stage, a gate number, or a team.

Approval is not a phase - it is the document status. A decision is not a phase - it goes in the implementation document. Full rules and examples: `references/how-to-split-phases.md`.

## What every phase carries

Four blocks, this order, no exceptions:

1. **Tasks** - one line each, with the date it was finished. **The last task of the last phase is always cleanup.**
2. **Acceptance** - what is observably true when the phase works. 2 to 6 lines.
3. **Unit test coverage** - a table mapping code this phase changed to the test file that covers it.
4. **Done when** - the five fixed lines D1 to D5. Never reword them.

D3 and D4 are the unit test gate. **A phase cannot be marked done while code it added has no unit test covering it.** See `references/coverage-gate.md`.

Cleanup happens **once, at the end of all phases**. It is the last task of the last phase, and it counts for D1 there, so the work item does not close until the disk it used is given back. Agents leave build output, simulator devices, logs and worktrees behind, and they add up fast - simulator devices alone are using 33 GB on this machine right now.

Earlier phases carry no cleanup task. They still record a disk baseline the moment they start, because the final cleanup needs it to tell what this work item created from what was already there. See `references/cleanup.md`.

## Two modes

### Create

1. Read the request and the code it touches.
2. Split the work into phases using `references/how-to-split-phases.md`.
3. Write the implementation document first - scope, what changes, what does not change, per-phase detail, per-phase coverage plan.
4. Write the tracker from it. The tracker's coverage rows are copied from the implementation document's coverage plan. Never invent a mapping.
5. Run `scripts/build-page.py <folder>`. It seeds `project-files/human/<slug>.html` from the template on the first run. Fill in only the header, the goal sentence and the approved-scope card there, then run it again. Everything per-phase is generated.
6. Set `status: awaiting-approval`. Stop. Do not start work.

Do not invent requirements. Write down assumptions. Ask about anything that changes scope.

### Maintain

1. Read the tracker, then the implementation section for the task you are about to do.
2. Check the tracker was approved.
3. Pick a task whose phase entry conditions are met.
4. Follow the matching recipe in `references/update-recipes.md`.
5. Record evidence in the implementation document. Record state in the tracker.
6. Rebuild the HTML page: `scripts/build-page.py <folder>`. It refreshes the stamp. Add any deviation, discovery or owner-decision entry by hand first - the builder keeps those word for word.
7. Run the checker. Non-zero exit means you may not hand over.

```sh
$(git rev-parse --show-toplevel)/.codex/skills/task-tracker/scripts/check-tracker.sh <work-item-folder> --base <sha>
```

## Status

Document status: `draft` -> `awaiting-approval` -> `approved` -> `in-progress` <-> `blocked` -> `completed`. Also `cancelled` and `superseded`.

**Never self-approve. Only the owner approves.** Record `approved_by`, `approved_at` and `approved_version`, and quote the owner's exact words in the implementation document. **If you cannot quote the words, you cannot set the field** - leave it `awaiting-approval` and ask. Start work only when `approved_version` equals `version`.

`approved` is the flag that tells every other agent it may write code. Setting it falsely is the worst thing this format can do. Recipe 0a in `references/update-recipes.md`, check 12 in `references/self-check.md`.

If scope changes materially, bump `version` and go back to `awaiting-approval`.

## Do not

- Do not put a paragraph in the tracker.
- Do not repeat the definition of done under every task. It belongs to the phase.
- Do not write "exit criteria". The concept is deleted. Phase acceptance covers it.
- Do not tick a coverage row for a test file that does not exist.
- Do not mark a phase done because the code was written. Written is not tested.
- Do not name a phase "Gate 2", "Implementation", "Testing", or "Polish".
- **Do not commit or push. Ever.** Commits belong to Hebert alone. No agent runs `git commit`, with or without a green gate. Finish the work, report it, stop.

Read `references/anti-patterns.md` for why each of these exists.

## A note on git

Because only Hebert commits, work in progress stays **untracked** for long stretches - sometimes days.

This breaks anything built on `git diff`, which never lists untracked files. It is exactly why the D4 gate unions committed, staged, unstaged **and** untracked paths. Do not "simplify" it back to one command, and never commit something just to make a check pass.

Reading git is fine - `git rev-parse HEAD` for a base commit, `git status`, `git worktree list`. Writing to git is not.
