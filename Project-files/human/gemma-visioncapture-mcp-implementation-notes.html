Gemma to VisionCapture MCP proof

A minimal host-controlled tool loop in the existing TurboFieldfare Mac chat, using the same loaded Gemma model and decode-service conversation while leaving VisionCapture and the model unchanged.

Requested scope
“Keep Agent Mode as the ordinary TurboFieldfare Mac chat with one optional high-level navigation tool. Gemma chooses only simple navigation intent. The Mac host privately owns the selected app and Simulator, VisionCapture sessions, cache refresh, execution grants, exact MCP requests, and result validation. Return only sanitized navigation facts to Gemma. Keep the first proof simple and do not integrate TurboFieldfare into VisionCapture.”

The existing Mac decode path needed a narrow tool bridge

The original AppGenerationRequest.swift and DecodeProtocol.swift had no tool fields. The approved architecture keeps the existing Mac chat and decode service, then adds only optional tool definitions, tool-call events, and tool-result continuation. It does not use or require TurboFieldfareServer.

Add an explicit in-session Agent Mode

MacAppSettings.swift persists one opt-in Agent Mode toggle, shown in the existing Inspector. The mode sends every prompt through the same AppModel, DecodeServiceInferenceClient, and loaded decode-service model as ordinary chat. Tools are available but optional. The first Agent Mode inference receives only a compact host-written navigation prompt and the high-level tool definition. The fixed local VisionCapture files are not placed in Gemma’s context. A normal prompt such as hi still produces a normal answer without requiring target configuration, reading those files, or opening an MCP connection. No external model server is started.

Visible change
One toggle plus bundle identifier and Simulator UDID fields that are required only when VisionCapture execution is requested.
Preserved
Load Model, Unload Model, sampling controls, the composer, transcript, status HUD, and user-pasted image path behave as before.
Boundary
Changing the mode requires an empty New Chat because the tool template belongs to one retained conversation. Target fields may change during ordinary idle chat, but the first accepted VisionCapture execution locks them until New Chat.

Implemented06

Expose one high-level navigation tool and keep VisionCapture protocol host-owned

VisionCaptureToolDefinitions.swift exposes only visioncapture_navigate. Gemma can choose launch, observe, tap, set_boolean, type, or back, with only the selector, role, Boolean state, or text needed for that choice. It cannot send an MCP request string, parameters object, target identity, session, grant, capability, digest, or raw VisionCapture payload. On the first requested navigation, VisionCaptureSkillReader.swift makes the host verify only the two generic local VisionCapture contract files. Their contents stay private to the host and are never added to Gemma’s prompt. The earlier bundle-to-guide mapping and target-specific execution requirement were removed. App knowledge may come from the user’s prompt or sanitized live observation, but it does not create a Swift code branch. The release binary carries a compiled checkout fallback so an installed app can find the copied generic files when launched outside the checkout. VisionCapture remains unchanged.

Why
A live run proved that Gemma could copy an observation grant into an action-capability field. Keeping those opaque protocol values in the host prevents cross-field relabelling and reduces Gemma’s task to choosing the next navigation step from sanitized evidence.
Acceptance
Traversal strings, symlinks outside the allowlisted local skill files, and arbitrary absolute paths never return bytes.

Add a loopback-only VisionCapture MCP client

Sources/TurboFieldfareApp/Core/Tools/VisionCaptureMCPClient.swift is created lazily only after Gemma requests visioncapture_navigate, the host validates the target, and the private local contract files are available. It then initializes JSON-RPC, verifies exactly one published tool named execute through tools/list, and sends the host-constructed sequential tools/call requests to VisionCapture’s inspected default endpoint, http://127.0.0.1:8766/mcp. Ordinary conversation never opens this connection.

Boundary
Only 127.0.0.1, only /mcp, only execute, with request timeout and response-size limits.
Acceptance
A proposed remote host, different path, or different MCP tool is refused without opening the connection.

Continue tool results inside the retained model conversation

MultimodalConversation.swift uses the existing Gemma tool renderer and StructuredAssistantDecoder. The decode service holds one conversation admission while assistant calls and host results continue against the same KV state, then commits one visible user-and-final-answer pair. The decoder remains strict by default. Only the app’s Agent Mode admits a syntactically valid call with an unknown tool name into this retained host-validation boundary, so the host can return a matched correction without losing the conversation. New Chat resets both the visible conversation and internal tool state.

Acceptance
Every result matches the pending call. A misspelled tool name is never executed or mapped to another tool: it appears as a local Not sent proposal, and a compact result under that exact pending call names visioncapture_navigate as the only permitted tool. Three consecutive identical mistakes use the existing local no-progress stop. Decode paths outside app Agent Mode retain strict unknown-tool rejection. A genuine failed tool run marks the lineage unusable, and New Chat is the recovery boundary.

Implemented11

Run one sequential host-controlled loop

Sources/TurboFieldfareApp/Core/Tools/VisionCaptureToolLoop.swift reads one high-level choice, validates it, privately refreshes VisionCapture cache state when needed, constructs and executes the exact permitted request, returns a sanitized result to Gemma, and repeats until Gemma answers or a factual terminal rule fires.

Stop rules
Final answer, user cancellation, MCP timeout or terminal refusal, context exhaustion, identity mismatch, malformed high-level proposal, or a request for an unsupported visual route. There is no arbitrary task-call cutoff. One Agent Mode inference stops as no progress after 2,048 consecutive generated tokens produce neither visible answer text nor a completed tool call; this conservative POC threshold allows a normal short proposal while preventing a hidden turn from consuming the remaining 64K context, and no new MCP request is dispatched from that stalled step. The same local proposal rejected three times on unchanged canonical sanitized screen content stops with its exact validation reason, even when other rejected proposals or read-only observations occur between attempts. A meaningfully changed screen or successful submitted operation clears that tracker. When no stable screen identity exists, the original three-consecutive-identical rule remains. At most 24 distinct rejection signatures are retained for one stable screen. Successful high-level observe choices have a separate bounded no-progress guard: the host retains only one SHA-256 digest and count for the canonical sanitized result. A changed result or successful dispatched mutation resets it. The third equivalent read returns one explicit correction to use a current action or editable-field selector, finish, or report a blocker. A fourth equivalent read after that correction ends the attempt with a precise read-only no-progress reason. This does not count internal recovery reads and is not a total tool or MCP-call limit. Three equivalent recoverable CACHE_COLD_MISS results for the same normalized host request also stop as no progress. A first or second cold miss with explicit dispatch_attempted=false remains recoverable, but the refused action is never replayed automatically. GUARDED_TARGET_REJECTED is returned to Gemma only when the public envelope consistently proves rejected_before_submission, submission_started=false, delivery_acknowledged=false, and DISPATCH_REJECTED_BEFORE_SUBMISSION. That exact high-level proposal is blocked only on the same observed screen content, and the bounded record holds at most 24 such proposals. Missing or conflicting proof, and GUARDED_DELIVERY_UNCONFIRMED, remain terminal. A host-generated cached action that returns CACHE_ACTION_CAPABILITY_STALE is recoverable only with explicit dispatch_attempted=false. The host discards the whole manifest, takes one plain read, and privately compares one unambiguous structured signature_fine. A changed screen returns cleaned facts for a new decision. An unchanged screen permits Gemma to choose the exact same action for the immediately available confirming bind only. Choosing another operation declines that confirmation and retires only that stale action on that screen; the different current operation remains eligible under its own evidence and history. A second stale refusal of the same action stops that action and the live cycle. A missing, invalid, or conflicting fine signature stops rather than weakening that fixed budget. Completed-cycle detection does not use the volatile fine signature. It uses one unambiguous signature_coarse plus a SHA-256 digest of canonical sanitized accessibility facts. When that bounded record proves that verified actions left and later returned to the same meaningful screen content, a proposal matching that completed cycle’s first fully represented action is rejected locally as NAVIGATION_CYCLE_REPEATED. No MCP request is sent, and Gemma receives a compact reason so it can choose a different current action. This is a proven-cycle guard, not a global task or action limit.
Acceptance
An ordinary Send action may return a final answer without using VisionCapture. The user’s prompt is the only goal. The same observe, sanitized-actions, Gemma-decision, and host-translation loop applies to every configured app. Gemma sees only visioncapture_navigate, receives no VisionCapture protocol values, and actual MCP calls never overlap.

Lock the target and keep sessions and cache evidence inside the host

VisionCaptureToolLoop.swift does not validate or require target fields for an ordinary chat turn. Only after Gemma requests high-level navigation does the host validate and inject the exact bundle identifier and Simulator UDID. The host alone retains one unambiguous returned session pair, refreshes the cache before each app-owned mutation, and holds the newest observation grant or exact action/revalidation capability. Gemma never sees or proposes any of those values. VisionCapture can return a new flow when an existing flow no longer resolves under its explicit-only policy, so a successful launch app, inspect cache, or describe screen response may roll the retained flow forward after target validation. A changed session from an error or mutation response remains terminal. Multiple conflicting returned pairs remain terminal, pairs split across separate objects are not joined, and a response without a clear pair does not create one. When the host’s own read-only inspect cache returns CACHE_LIVE_VALIDATION_FAILED, the adapter treats it as pre-dispatch only when dispatch evidence is absent or explicitly false, never true or conflicting. It discards the cache handles and sends VisionCapture’s existing describe system alert read. One unambiguous present alert becomes sanitized title-and-button facts. Gemma still chooses an ordinary high-level tap whose role is system_alert_button; the adapter then sends VisionCapture’s existing press system alert button once with the private exact label and digest. Neither alert request carries a flow session. If the alert read proves no native alert is present, the host sends one plain read-only describe screen without a cache grant or capability and returns only sanitized facts. It does not repeat inspect cache or retry the discarded action. For stale cached-action recovery, VisionCapture’s structured payload.view.signature_fine remains private and exists only to prove exact changed versus unchanged state. The adapter accepts only one unambiguous fine value and does not weaken that comparison. Separately, bounded no-progress memory uses the public coarse signature plus a digest of sorted, de-numbered sanitized accessibility facts. This ignores session and fine-signature churn but changes when meaningful visible controls, roles, labels, or structural selection change. A ready or revalidation cache block can publish actions without a fine signature. When that happens after a mutation cleared the previous identity, the adapter conditionally discards those handles, makes one plain target-bound describe screen, records both private identities, then calls inspect cache once for fresh usable handles. VisionCapture’s public contract does not accept its output-only screen_capability as a read input, so the adapter never relabels or sends it. No extra describe is added when the current fine identity already exists, and the cold observation-grant route remains unchanged. Gemma receives the comparison result and an optional single confirming high-level action, never either signature, the digest, or a discarded capability.

Pre-dispatch checks
A tap or switch change must match exactly one selector, role, and requested state in the newest host-held manifest. A named type action must match exactly one visible, enabled editable element from the newest structured screen description, using the exact published label or identifier selector kind. The host keeps those selector kinds distinct and never infers, remaps, or relabels a field. VisionCapture can safely type without a named selector only when current focus is proven, but the current sanitized screen contract does not publish that proof. The adapter therefore does not accept a selector-free type proposal. Missing or ambiguous evidence fails closed before MCP dispatch.
Native-alert contract audit
The generic adapter already implements the required sequence exactly: one session-free describe system alert; one unambiguous returned alert whose enabled visible button label Gemma selects; one session-free press system alert button carrying that exact private label and the same response’s content_digest; then one session-free read-only describe system alert. The host clears the current digest before dispatch, so it cannot submit the press twice. Every other SYSTEM_ALERT_* refusal ends the alert attempt. SYSTEM_ALERT_TAP_DELIVERY_UNKNOWN alone permits the single read-only follow-up, records the uncertain digest, and blocks every later press while that same digest remains. The high-level schema publishes no pointer operation, and no activate, show, move, click, or hide request exists in this adapter.
Acceptance
Missing identity does not block normal chat and stops only the requested navigation. The application and Simulator target never roll. Session replacement is limited to one unambiguous flow identity from a successful read-only continuation request. Mutation results, error results, learning-session changes, and conflicts remain terminal. The newest terminal cache replaces prior single-use state. An alert digest is retired before its one press; the host automatically performs a read afterward, never retries SYSTEM_ALERT_TAP_DELIVERY_UNKNOWN, and treats every other SYSTEM_ALERT_* refusal as terminal. Only sanitized screen or alert facts, available selector-and-role actions, and proof outcome return to Gemma.

Preserve the existing chat, status, and image experience

Agent Mode does not replace the chat placeholder, transcript, status HUD, Generate and Stop controls, or image-paste path. User-pasted images still flow through the existing vision companion when installed. The transcript adds display-only activity entries for every actual VisionCapture request, including private cache, description, revalidation, and system-alert adapter steps. Each entry shows the exact host-locked outgoing MCP request and its status together in a bordered monospaced code card. A locally rejected high-level Gemma proposal is labelled Not sent and not an MCP request, with readable proposed JSON and the exact validation reason. Raw MCP response bodies and returned image data are not added.

Conversation boundary
Activity entries live in separate AppModel transcript state. They are never appended to AppConversation, tool results, decode-service requests, or the model KV conversation.
Acceptance
Requests and statuses stay in execution order. Send remains disabled during the loop, Stop cancels the active model or MCP step, and New Chat clears the retained tool and activity state.

Live proof completed · exploration blocked by cache binding14

Build and live-proof one driver-only journey

The deployed proof passed its bounded safety goal. Gemma completed all six onboarding steps, handled two native alerts through the exact dedicated route, entered Add Profile, and tapped Done without manual target interaction or a pointer. VisionCapture then returned CACHE_ACTION_CAPABILITY_STALE twice for the same action on the unchanged screen. The host enforced the one-confirming-attempt rule and stopped at that factual boundary without sending further input. The full-app exploration is therefore not complete; it remains blocked by the VisionCapture cache-binding product bug rather than by an arbitrary Agent Mode task limit.

Deployment evidence
The installed app passed signing verification and matched both staged dist binaries. The clean NestMind reinstall used the existing Simulator artifact. TurboFieldfare started with a fresh chat and freshly loaded model.
Runtime configuration
64K context, 32 expert-cache slots, temperature 0.20, Top-K 64, Top-P 0.95, Prefill on, and RDADVISE off.
Journey evidence
All six onboarding steps completed. Each of the two native alerts followed describe system alert → one exact Allow press carrying the returned digest → one read-only describe system alert. No pointer request was used. The run reached Add Profile, submitted Done, then stopped after the second stale refusal for the same unchanged-screen action. The terminal context reading was 4.6K of 66K with 32 tool calls.
Memory evidence
/tmp/turbo-alert-cycle-retest-memory.csv contains 63 samples. Combined process memory peaked at 2,409,872 KB and averaged 1,117,349 KB. The app peak was 155,632 KB and the decode-service peak was 2,319,856 KB.
Remaining blocker
The proof cannot claim full-app exploration until VisionCapture resolves the repeat CACHE_ACTION_CAPABILITY_STALE cache-binding failure on an unchanged screen. No additional source change, rebuild, deployment, unit test, live run, commit, or push was performed while recording this verification.
Later ordered-run finding
A later clean ordered run completed onboarding and both alert routes, then stopped after Gemma proposed the same named type target three times. One misspelled tool name was correctly returned as Not sent. The repeated target was also never sent. The failure was in the adapter: VisionCapture’s describe screen result publishes visible editable elements in structured elements with exact labels and identifiers, while TurboFieldfare discarded those fields and incorrectly checked typing against the cache action list used for taps and switches. Observing again therefore could not provide a valid type target. The run ended at 4,942 total tokens and 39 tool calls. /tmp/turbo-ordered-nestmind-memory.csv contains 62 samples: combined peak 2,034,640 KB, combined average 1,224,680 KB, app peak 172,320 KB, and service peak 1,938,256 KB.
Typing correction
The generic adapter now retains a bounded sanitized available_text_fields list from the latest exact fine-screen observation. It includes only unambiguous visible, enabled text_field or secure_text_field entries and pairs each selector with selector_kind: label or identifier. The high-level schema and compact recovery result tell Gemma to copy that exact pair. Host validation requires one exact match before constructing the private VisionCapture type request. The existing third-repeat stop is unchanged. This correction has been release-built only; it has not been deployed or live-tested.
Later read-only loop finding
In the next clean ordered run, Gemma completed onboarding and both native alerts, reached the profile area, then chose the high-level observe operation roughly 30 times on unchanged sanitized screen content with no intervening action. Gemma cannot choose or see a raw inspect cache operation; each visible inspect cache request was the host’s internal translation of observe. Those reads succeeded, so the existing malformed-proposal, refusal, stale-action, and completed-mutation-cycle guards correctly did not classify them, but no read-only repetition guard existed. Manual cancellation caused the final NSURLError -999; that interrupted request was not the root failure.
Read-only correction
The schema, developer prompt, and every successful sanitized observation now say that observe is one refresh rather than a waiting loop. When current choices exist, the result points Gemma directly to available_actions and available_text_fields; when none exist, it asks for a final answer or factual blocker. A per-run tracker hashes only the canonical sanitized result and retains one digest, count, and correction flag. The third identical successful observation adds one matched correction. If Gemma requests and receives the same unchanged observation again, the fourth ends with a factual no-progress error. A changed sanitized screen or successful mutation resets the tracker. Internal native-alert and stale-cache recovery reads are not counted. This correction has been release-built only; it has not been deployed or live-tested.

Future plan · parked15

Discuss a larger context option after the first proof

Keep 64K as the selected context for the first proof. In a separate follow-up, consider adding a larger option for Macs with more available unified memory. The requested target is around 120K. Before implementation, choose between an exact 120K value and the standard 128K boundary, measure a real model load and short generation, and agree how the app should warn when memory pressure is too high.

Current evidence
The app currently stops at 64K. Its existing KV-cache formula estimates 120K at +2.35 GB versus the 8K default, or +1.17 GB beyond 64K. A 128K option estimates +2.52 GB versus 8K, or +1.34 GB beyond 64K. These figures do not include model weights, expert-cache slots, Metal scratch allocations, the optional vision tower, or other process memory.
Boundary
Do not add this option during the first proof. Do not treat the estimate as runtime validation. Discuss the exact token boundary, supported hardware, user warning, and acceptance measurement before changing AppContextLengthOption.swift, ServerArguments.swift, or their tests.
Model limit
The official Gemma 4 26B-A4B model card states a 256K context length, so both proposed values are inside the model specification. TurboFieldfare support above 64K is not yet proven.
