Gemma to VisionCapture MCP proof

A minimal host-controlled tool loop in the existing TurboFieldfare Mac chat, using the same loaded Gemma model and decode-service conversation while leaving VisionCapture and the model unchanged.

Requested scope
“Keep Agent Mode as the ordinary TurboFieldfare Mac chat with optional tools. When the user asks to test an application, Gemma requests the existing VisionCapture skills through a controlled file tool, then prepares function calls that the Mac host validates and forwards to VisionCapture’s local MCP server for the selected app and Simulator. Keep the first proof simple and do not integrate TurboFieldfare into VisionCapture.”

Finding · confirmed01

The existing Mac decode path needed a narrow tool bridge

The original AppGenerationRequest.swift and DecodeProtocol.swift had no tool fields. The approved architecture keeps the existing Mac chat and decode service, then adds only optional tool definitions, tool-call events, and tool-result continuation. It does not use or require TurboFieldfareServer.

The parser and native Gemma tool format already exist

StructuredAssistantDecoder.swift, GemmaToolCallParser.swift, and GFTokenizer.FunctionDefinition already decode native Gemma calls. TurboFieldfareServer/Core/ServerInference.swift is the working reference for rendering tools and returning structured calls.

Finding · confirmed + inference04

Agent Mode must preserve the loaded runtime configuration

Agent Mode uses the model session that the existing Load Model control created. Context length, expert-cache slots, temperature, Top-K, Top-P, prefill, RDADVISE, image support, and the other current app controls continue to apply unchanged. The normal request validation and retained-conversation context limit remain the gate. No second model profile or server startup configuration is introduced.

Implemented05

Add an explicit in-session Agent Mode

MacAppSettings.swift persists one opt-in Agent Mode toggle, shown in the existing Inspector. The mode sends every prompt through the same AppModel, DecodeServiceInferenceClient, and loaded decode-service model as ordinary chat. Tools are available but optional. A normal prompt such as hi produces a normal answer without requiring target configuration, reading skills, or opening an MCP connection. No external model server is started.

Visible change
One toggle plus bundle identifier and Simulator UDID fields that are required only when VisionCapture execution is requested.
Preserved
Load Model, Unload Model, sampling controls, the composer, transcript, status HUD, and user-pasted image path behave as before.
Boundary
Changing the mode requires an empty New Chat because the tool template belongs to one retained conversation. Target fields may change during ordinary idle chat, but the first accepted VisionCapture execution locks them until New Chat.

Implemented06

Expose compact tools and allowlisted local skill reads

VisionCaptureToolDefinitions.swift and VisionCaptureSkillReader.swift expose fixed names for this checkout’s .codex/skills/vision-capture/SKILL.md, efficient-exploration skill, and local reference/index.md. The reader is created lazily only after Gemma requests the read tool. The release binary carries a compiled checkout fallback so an installed app can find these copied files when launched outside the checkout. VisionCapture remains unchanged.

Why
The raw VisionCapture tools/list schema contains forms that are not directly accepted by GemmaToolSchema. A small wrapper schema avoids both incompatibility and unnecessary context cost.
Acceptance
Traversal strings, symlinks outside the allowlisted local skill files, and arbitrary absolute paths never return bytes.

Implemented07

Add a loopback-only VisionCapture MCP client

Sources/TurboFieldfareApp/Core/Tools/VisionCaptureMCPClient.swift is created lazily only after Gemma requests visioncapture_execute and the host accepts the target. It then initializes JSON-RPC, verifies exactly one published tool named execute through tools/list, and sends sequential tools/call requests to VisionCapture’s inspected default endpoint, http://127.0.0.1:8766/mcp. Ordinary conversation never opens this connection.

Boundary
Only 127.0.0.1, only /mcp, only execute, with request timeout and response-size limits.
Acceptance
A proposed remote host, different path, or different MCP tool is refused without opening the connection.

Implemented08

Carry optional tool turns through the existing decode service

AppGenerationRequest.swift and DecodeProtocol.swift now carry an optional tool-aware user step or matched tool results. AppInferenceEvent and DecodeServiceEvent can return a structured tool call with its name, ID, and JSON arguments. Requests without these optional values keep the ordinary chat path.

Why
This is the minimum protocol change needed to return host tool results to the same model process and retained KV conversation.
Acceptance
A Gemma tool call reaches the Mac host intact, and every result must match the pending call ID and name.

Implemented09

Keep one loaded model and the existing chat session

Sources/TurboFieldfareApp/Core/State/AppModel.swift runs Agent Mode through the same request preparation, retained images, decode client, and loaded runtime as normal chat. Enabling the mode does not unload, reload, replace, or block the app model, and it does not start a second model process.

Rejected route
A separate TurboFieldfareServer process and a second model-loading workflow.
Acceptance
The existing Load Model and Unload Model controls remain available, and one decode-service model owns every ordinary and tool-aware turn.

Implemented10

Continue tool results inside the retained model conversation

MultimodalConversation.swift uses the existing Gemma tool renderer and StructuredAssistantDecoder. The decode service holds one conversation admission while assistant calls and host results continue against the same KV state, then commits one visible user-and-final-answer pair. New Chat resets both the visible conversation and internal tool state.

Acceptance
Every result matches the pending call, a failed tool run marks the lineage unusable, and New Chat is the recovery boundary.

Implemented11

Run one bounded host-controlled loop

Add Sources/TurboFieldfareApp/Core/Tools/VisionCaptureToolLoop.swift and call it from Sources/TurboFieldfareApp/Core/State/AppModel.swift. It reads a call, validates it, executes it, returns the result to Gemma, and repeats until Gemma answers or a terminal rule fires.

Stop rules
Final answer, user cancellation, fixed 16-call limit, MCP timeout or refusal, context exhaustion, identity mismatch, malformed call, or a request for unsupported visual evidence.
Acceptance
An ordinary Send action may return a final answer with no tools. When Gemma requests VisionCapture execution, the host requires the three ordered instruction reads first, then returns each result to the same model conversation. Calls never overlap.
12
Implemented12

Lock the selected application and Simulator

VisionCaptureToolLoop.swift does not validate or require target fields for an ordinary chat turn. The fields remain editable while no turn is running. Only after Gemma requests visioncapture_execute does the host validate the exact bundle identifier and Simulator UDID, inject both into the VisionCapture request, and enforce the target established by the first accepted execution. Missing or conflicting identity becomes a structured host tool error returned to Gemma, with no MCP dispatch or device input. Capabilities, grants, session IDs, and proof fields remain opaque and unchanged.

Acceptance
Missing identity does not block normal chat and stops only the requested VisionCapture action. A later execute call cannot change either locked value. payload.proof.verdict controls continuation where the skill requires it.

Implemented13

Preserve the existing chat, status, and image experience

Agent Mode does not replace the chat placeholder, transcript, status HUD, Generate and Stop controls, or image-paste path. User-pasted images still flow through the existing vision companion when installed. Internal tool arguments, capability values, response bodies, and image data are not added to the visible transcript.

Acceptance
Send remains disabled during the loop, Stop cancels the active model or MCP step, and New Chat clears the retained tool state.

Future plan · parked15

Discuss a larger context option after the first proof

Keep 64K as the selected context for the first proof. In a separate follow-up, consider adding a larger option for Macs with more available unified memory. The requested target is around 120K. Before implementation, choose between an exact 120K value and the standard 128K boundary, measure a real model load and short generation, and agree how the app should warn when memory pressure is too high.

Current evidence
The app currently stops at 64K. Its existing KV-cache formula estimates 120K at +2.35 GB versus the 8K default, or +1.17 GB beyond 64K. A 128K option estimates +2.52 GB versus 8K, or +1.34 GB beyond 64K. These figures do not include model weights, expert-cache slots, Metal scratch allocations, the optional vision tower, or other process memory.
Boundary
Do not add this option during the first proof. Do not treat the estimate as runtime validation. Discuss the exact token boundary, supported hardware, user warning, and acceptance measurement before changing AppContextLengthOption.swift, ServerArguments.swift, or their tests.
Model limit
The official Gemma 4 26B-A4B model card states a 256K context length, so both proposed values are inside the model specification. TurboFieldfare support above 64K is not yet proven.

Decision · confirmed16

Keep the first proof accessibility-only

The implemented boundary is bounded, driver-only, and accessibility-only. VisionCapture screenshot, Computer Use, pointer, preview, recording, and visual-bypass requests stop before forwarding. This does not disable the existing chat image path: images pasted by the user still reach the same loaded model through the installed vision companion. Transporting images returned by VisionCapture remains outside this proof.
