Astra independent multi-token decision — 2026-10-02

The causal lookup run establishes no speed result: decision-001.json records OFF terminated at 29% free after 16.025 s, no completed generation, and ON unrun. Keep the 30% guard and do not immediately repeat it. The warm pair ratios 0.912/0.944 are negative evidence about the current verifier, not a hardware limit or a measurement of native MTP.

Selected design: a trained, single-draft MTP proposer feeding an exact two-input verifier, with the first token's recurrent boundary emitted inside the existing grouped computation. This replaces both weak history-copy proposals and full-prefix replay. It is a bounded architecture experiment, not a claim that two-token decoding can deliver 20 tokens/s. Do not build the native head by guessing its input alignment.

Its forward normalizes the embedding and hidden input separately, concatenates them, projects to hidden size, runs a full-attention MoE layer, then normalizes and uses the language head. Tensor names alone cannot settle these.

Causal correctness
At a cycle boundary, one target-sampled token is pending. The proposer sees only committed target state and that pending token. Verify [pending, draft]. Sample the target's first row with the normal target history and sample position. On mismatch, retain only the pending input's exact state and leave the correction pending. On agreement, accept the draft input and sample the second row for the next pending token. EOS remains unconsumed. Do not sample discarded target rows or advance the target random stream for proposals. For stochastic settings this requires the same target sampling sequence, not merely equal argmax or equal distributions.
The MTP cache requires explicit causal catch-up. Accepting the second input must not leave its MTP history absent, and a rejected speculative suffix must not remain in that cache. Count prompt initialization and any accepted-token catch-up/head work. The pinned caller trace determines which hidden row and position to use. Tools, reasoning and image positions retain their existing target path. An initial text-only probe does not qualify those other paths.

Memory budget, not a headroom claim
Shape-derived additional storage is approximately 75 MiB of BF16 nonexpert MTP weights, at most 48 MiB for eight expert pairs, 32 MiB FP32 MTP KV at context 8192, and 63.75 MiB for one target recurrent/convolution prefix boundary: roughly 219 MiB plus measured scratch. Shared embedding/head storage must remain shared. Never retain all MTP experts (about 1.5 GiB BF16). At 64K the extra KV is 256 MiB, making this estimate roughly 443 MiB plus scratch. Existing rollback state is additional baseline storage, not free space. The OFF abort means neither budget is presently admitted. No background-app killing, reduced context or lowered guard is justified by this estimate.

Decisive timing gate
Let S be serial target time per consumed input, V2 actual two-input verification wall, D all proposal plus amortized prompt/catch-up work, a actual draft acceptance, and R rejection settlement cost. Steady cycle cost per advanced input is approximately (V2 + D + (1-a)R)/(1+a), with exact whole-request counting for initial/final pending tokens. Measure the actual causal chain, not this formula alone.
At a=0.8 and D=0.1S with negligible R, a 10% gain requires V2 <=1.52S. If the four-input warm ratio transferred to two inputs, V2 would be about 1.89S: almost no gain even at perfect acceptance and this cheap proposer. Transfer is unproven, so do not present it as a measured two-input result. A one-draft design has an ideal 2x ceiling if verification were free beyond one serial step. From about 1.5 tokens/s it cannot explain 20. At 20 tokens/s the whole two-output cycle must fit 100 ms; the present verifier is far from that. A passing small gain would justify investigating wider trained drafts and genuinely shared verification, not asserting the goal achieved.

One experiment, after the reference and resource prerequisites: fresh OFF serial versus ON native-one-draft/two-input causal generation on a predeclared representative request, with existing replay available only as a failure fallback and every fallback charged. Include proposer initialization, proposal, verification, sampling, prefix selection, catch-up and rollback in time-to-complete and report decode separately. Compare exact committed IDs, accepted target raw rows/routes, final recurrent/KV state and source-check counts. Record minimum system free and peak owned storage. No teacher-forced/future-token input is an ON result. A useful result requires at least 10% lower full decode wall in both orders, nonregressing total request time, exact state, and >=30% free. Stop on first integrity/resource failure or first nonimproving arm. No width/threshold sweep on the 29-token trace.

Why this choice rather than the alternatives
Prompt processing batches known tokens and has a different source-observation contract; its speed cannot be assigned to speculative decode. The lookup screen's 13/27 accepted drafts is not evidence about a trained MTP head. Prefix snapshots alone remove replay but do not fix low acceptance or expensive verification. Progressive lookup pairs can avoid some rejected work but remain tied to that weak proposer. The rejected source64 token4 kernel is not a demonstrated shared-compute speedup and should not be retried under a new name.

Recommendation: establish the native caller recurrence before implementation, then consider this one tightly bounded trained-proposal/two-input experiment only with measured memory admission. No currently completed evidence supports a practical exact change reaching 20 tokens/s, and no result here justifies speculative head code or relaxing correctness.
