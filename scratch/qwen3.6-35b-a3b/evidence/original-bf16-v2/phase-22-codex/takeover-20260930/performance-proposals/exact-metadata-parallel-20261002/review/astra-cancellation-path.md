Smallest safe mechanism: create one typed Sendable cancellation-latch object at produce entry and wrap the existing produce body in withTaskCancellationHandler(operation:onCancel:). Keep actor isolation on the operation. onCancel only sets a mutex-protected monotonic Bool and returns. It must not touch actor state, close FDs, cancel tasks, resume continuations, call hooks or wait for workers. The lock protects only the Boolean. Retain the latch through the operation and all joined lanes.

Pass the latch explicitly through produceToken and moeStep to the receipt-validation entry point. Do not place it in model-global mutable state, infer it from a nonnil closure, or obtain it by escaping UnsafeCurrentTask. Calls outside this narrow produce scope, including prefill, beginTurn, sampler and no-receipt fallback, remain serial. The existing produce timing-wrapper recursion must forward the same latch, not create a disconnected replacement.

Pending/initial cancellation: preserve the existing argument/position guards and their error order. The cancellation handler sets the latch even if the task was already canceled when installed, but the operation still executes, so retain the existing Task.checkCancellation before initial validation. Before each worker entry, inspect the latch instead of the worker’s Task.isCancelled. No fresh file open occurs after that entry observes cancellation.

Cancellation while running: a file already opened completes its original stat/compare/remember sequence and deferred close, just as cancellation between the existing serial per-entry checks does. At the next entry boundary, record CancellationError at that receipt index and stop starting later entries in that lane. Already submitted lanes must still terminate and join. Never return from the caller, start the next scan, or release handle/lease ownership while a lane can still hold an FD.

Join/error rule: collect the lowest receipt-index outcome among filesystem errors and cancellation observed BEFORE an entry. Drain all lanes first. Throw that outcome before any later root/binding work. If no indexed failure exists, retain caller Task.checkCancellation/final binding checks before returning success, covering cancellation that arrived after the last worker entry. Do not blanket-prefer a late cancellation over an already recorded source error. This is deterministic and cancellation-safe, but does not claim identical error precedence for all serial-versus-parallel timing races. That existing limitation must remain explicit.

No new suspension in the critical interval: the handler is installed around the whole produce operation, not around each post-map validation. The actual validator remains synchronous and joins workers with the existing blocking DispatchGroup wait. After successful post-map validation, allocation/encoding/commit remains the same synchronous sequence. Cancellation after the final check remains subject to the existing pre-submit checks and post-submit settlement; the latch does not promise cancellation atomic with GPU commit.

Swift’s documented semantics support this: an already-canceled task invokes onCancel before operation, cancellation during operation invokes it concurrently, and installing the handler itself does not suspend before operation. See [Apple cancellation-handler documentation](https://developer.apple.com/documentation/swift/withtaskcancellationhandler(operation:oncancel:isolation:)). No caller cancellation bridge is added for shouldStop: retain its current token-boundary semantics and do not run that arbitrary closure on metadata workers.

Concrete acceptance prerequisite for Sol’s staged design: one latch per produce call, no lock held over filesystem work or join, all submitted lanes closed/drained on every outcome, explicit indexed-error selection, and an unchanged synchronous post-map-to-submit path. No code, tests, builds or runs were performed. The narrow cancellation mechanism is feasible; retain serial fallback everywhere outside its proven lifetime.
