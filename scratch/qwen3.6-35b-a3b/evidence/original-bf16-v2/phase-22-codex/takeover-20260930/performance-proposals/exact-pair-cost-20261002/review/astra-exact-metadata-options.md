Decision: do not stage either retained-FD-only or bulk-metadata-only validation as an exact production substitute. Both omit a current fresh-open observation. A small metadata-only primitive cost experiment is justified to identify a viable implementation target, but the proposed substitutions are not yet semantically equivalent. No permission or correctness concession is needed or requested.

Current contract, OfficialSourceHandle.validateTrustedReceipt: validateBinding; receipt/path/digest/inventory checks; scan; validateBinding; second scan; validateBinding. Each scan checks held and freshly named root fingerprints before and after, lists names to EOF with existing spelling/decoding semantics, checks cancellation before each sorted receipt entry, then openat(O_RDONLY|O_NONBLOCK|O_NOFOLLOW|O_CLOEXEC), fstat, named fstatat(AT_SYMLINK_NOFOLLOW), regular-file/single-link checks, full fingerprints, held/named identity equality and remember. The fixture explicitly expects 39 receipt files, not 46. Directory-listing count must not be substituted for receipt.files.count when estimating savings. At N=39 this is 78 fresh file opens and closes per validation, plus 156 file stat calls and the unchanged surrounding checks.

Retained descriptors: fresh fstat(held) plus fresh fstatat(name) in the same per-entry order would preserve ordinary persistent replacement/unlink/symlink, truncation, size, mode, mtime/ctime and link-count rejection, provided ALL current comparisons and both scans remain. A file changed after initial opening is not accepted merely because its descriptor is retained. A normal chmod or ACL update that changes ctime is also caught. It would be incorrect to claim these simple changes alone establish a bypass.

Concrete missing observation: read access can change without any receipt inode metadata changing. For example, after opening an owner-readable file in world-searchable/readable directories, changing the process’s effective credentials can leave fstat and fstatat permitted while a new O_RDONLY open returns EACCES. An authorization policy or external group-membership change is another class requiring investigation. The handle does not prove immutable credentials/authorization. A previously opened descriptor therefore cannot prove that today’s open would succeed. Apple’s open path authorizes READ_DATA separately from merely obtaining attributes: https://github.com/apple-oss-distributions/xnu/blob/main/bsd/vfs/vfs_vnops.c . This is a concrete semantic difference, not a claim that the production app currently changes UID.

Fresh access()/faccessat() or ATTR_CMN_USERACCESS is not automatically an exact replacement for open: credentials/options, sandbox/open policy, vnode-open failures and the observation point must match. A new open followed by close preserves the missing read-open check but gives back the proposed syscall saving. Ordinary mode-change failure also changes from “file unavailable” at open to “file changed” after stat, even when both versions reject. Retained descriptors additionally alter behavior under descriptor exhaustion and filesystem revocation. Successful unchanged-file runs cannot settle these differences.

Ownership if retained descriptors are explored later: bind one immutable filename-to-owner array to this handle AND the fully validated receipt, not just a source path or a globally reused receipt. Bound it to N receipt entries. Keep O_CLOEXEC, close each owned descriptor once on partial initialization failure or deinit, never expose numeric FDs, and retain the owner through concurrent validation calls. Fresh fstat does not move a file cursor. Independent directory scans still need their own opened cursor. Lazy publication needs one atomic complete owner set, not partially shared slots or a long global lock. Eager construction adds N opens and can fail earlier than today; lazy first-use construction changes first-call resource behavior and must preserve cancellation/cleanup. About 39 additional long-lived descriptors are small in data bytes but consume kernel resources and pin inodes. They are not free memory or a new weight cache.

getattrlistbulk: the installed MacOSX26.5 SDK manual and Apple source describe unspecified entry order, required NAME/RETURNED_ATTRS, per-entry ERROR, potentially omitted attributes, and symlink-object rather than target attributes. It is not documented as an atomic directory snapshot. Primary reference: https://github.com/apple/darwin-xnu/blob/main/bsd/man/man2/getattrlistbulk.2 . It cannot alone provide the current independently held-file observation or read-open authorization.

Required field mapping would include DEVID, FILEID (not deprecated OBJID), OBJTYPE, ACCESSMASK, MODTIME, CHGTIME, FILE_LINKCOUNT and FILE_DATALENGTH. ACCESSMASK supplies permission bits only, so the complete st_mode comparison needs correct type reconstruction. TOTALSIZE includes all forks and is not the current st_size comparison. Every required returned-attribute bit and per-entry error must be checked, with bounded record/name offsets and the existing String decoding/equality. Apple field definitions: https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/getattrlist.2 . Missing fields require a current-method fallback, never defaults treated as observations.

Bulk collection also moves observations ahead of the sorted per-file cancellation/open/stat sequence. Sorting returned records can preserve reported filename order but cannot make earlier buffered attributes into the later named lookup. Keeping both root checks, both scans, live bindings and marker reads remains necessary. Persistent mutation may still be caught by fingerprints, but that does not prove identical transient/error/access observations. Adding fresh held and named stats plus fresh opens after the bulk call retains safety while removing little of the expensive current work.

Prior work considered: APP20 opus-validation-cost-followup targets validateRetainedFile hit/publication checks and proposes immutable identity, ASCII-name and marker-buffer work. It estimates only 0.1–0.26 seconds per 32-token decode and does not prove these receipt-scan substitutions. COST now measures about 0.395 seconds of direct checks per four inputs, but does not separate open/close, stats, listings or bindings. The existing MetadataCostDiagnosticTests reports whole validation and reads expert payload, so it is neither the required primitive breakdown nor appropriate to rerun for this question.

One justified next metadata experiment, before any production candidate: a standalone bounded read-only breakdown of the existing validateTrustedReceipt loop, preserving all calls and their order, reporting fresh file open+close, held stat, named stat, listing, root/binding/marker work and overall elapsed/CPU separately. Include initialization and steady-state observations, alternate instrumented/control passes, no tensor admission or payload reads, no new unit-test lines. Main must authorize/run it separately. If open/close consumes less than half the approximately 0.10 seconds/input, eliminating it could not even meet the 0.05-second total budget with all other model work unrealistically free. That is a useful falsifier of this particular direction, not a hardware floor.

The current per-input check cost warrants investigation beyond progressive verification. It does not justify weakening fresh-open rejection, treating cached attributes as live, or claiming the cost is irreducible. Neither proposed replacement is ready for a performance trial as an exact validator.
