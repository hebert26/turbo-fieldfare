# Next critical path

No scheduler patch. The 87 ms figure is serial idle after commit, and the part that repeats is the first shader start after a host gap of at least 2 ms. Prefetch does not remove that start. Keep-warm stays closed. Do not code command fusion or an early MoE commit.

Source is `f210c70`. The clocks are the app019 known-none OFF decode, `expert-read-app-trial-20261002/qwen-read-known-none-off-app-001-strict-analysis.stdout.json`, checked against its runtime measurement rows. `submit_before_gpu_sum_ns` is 2790260034.75. That is 2.790260 s, or 87.20 ms across 32 tokens. It is a sum of 4434 per-command gaps (`gpuStart` minus `willCommit`). On this schedule the sum is critical-path time: the gap overlaps no other GPU interval, and all 4433 later commands are submitted only after the previous `gpuEnd`. `QwenOfficialSourceRunner.settle` and both `QwenTextRunner` `submitAndSettle` methods wait for `command.completed` before the next encode. A later overlapped schedule must not treat this sum as savings.

The sum is not 87 ms on every token. Positions 1055–1057 hold 1.567 s of it. 1.485 s of that is the Metal `kernelStart`–`kernelEnd` driver interval (a CPU scheduling window before the shader). Positions 1058–1085 hold 1.223 s, which is 43.67 ms per forward. Inside that steady gap, `commit` is 6 µs per command. The driver interval is 9.2 ms per forward. `kernelEnd` to `gpuStart` is 32.3 ms per forward. Shader time is separate and is not part of this gap.

The steady 32.3 ms sits on commands that follow a long host gap. Every steady MoE command follows at least 2 ms of idle, mostly the expert map. MoE submit-to-GPU-start is 481 ms, 17.2 ms per forward, and its `kernelEnd`-to-`gpuStart` median is 285 µs. The map wall is 9.220261 s over 1240 maps, 7.44 ms each. The same median is 300 µs on `full_gate_output` after the 2–5 ms CPU attention gap, with no expert buffers. Router and the prepared linear step follow under 2 ms of idle. Their medians are 49 µs and 55 µs. The delay is a step after roughly 2 ms of GPU idle. It does not grow from a 5 ms idle to a 20 ms idle. A 66.94% miss-recall prefetch leaves this map above 2 ms, so the MoE start delay remains. The 92 ms screen is a different, hypothetical read-overlap score. It is not this gap.

`moeStep` in `Sources/TurboFieldfare/Runtime/Qwen/QwenOfficialSourceRunner.swift` awaits `coordinator.map`, calls `revalidateSource`, then `QwenMoE.submitExpertsBF16`, then `settleSubmitted`. Slot binding exists only when `map` returns, so the MoE command cannot be committed during the map without using expert bytes before the post-map check. The first command after the idle pays the delay. A shared-expert command before it would add a commit and move the same delay. Full-attention QKV and norm/RoPE are the only GPU pair with no math between them (`QwenTextRunner` full `append`: await QKV, copy query/gate on the CPU, await norm/RoPE). Their steady QKV submit-to-GPU-start sum is 2.30 ms per forward. That is below the bar.

Experiment: no source change. On any later captured decode with these same clocks, including the prefetch pair, read steady forwards from the fourth onward. Reject a scheduler, fusion, or early-commit patch unless the steady MoE `kernelEnd`-to-`gpuStart` median is under 80 µs and the steady submit-to-GPU-start sum is under 20 ms per forward, with the same token IDs, at least 30% free memory, and no keep-warm kernel. A median still at or above 200 µs, or a steady sum still at or above 35 ms per forward, closes this gap. Main chooses. Sol does not code a critical-path patch from this note.
